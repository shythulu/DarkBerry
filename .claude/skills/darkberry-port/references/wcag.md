# WCAG brief for the accessibility auditor

A colour theme controls colour only. It can fail five WCAG criteria and no others. Audit
those five, trust `docs/CHECKS.md` for what the build already proves, and report in the
format at the end. Run `scripts/cvd.mjs --roles all` once per review for the baseline.

## What a theme can and cannot fail

| Criterion | Theme can fail it | Why |
|---|---|---|
| 1.4.3 Contrast (minimum) AA | yes | text and background colours are the theme's |
| 1.4.6 Contrast (enhanced) AAA | informational only | Darkberry targets AA; report 7:1 misses as notes, never findings |
| 1.4.11 Non-text contrast AA | yes | focus ring, borders, cursor, state fills are the theme's |
| 1.4.1 Use of colour A | partly | the theme picks the hues; the app decides whether a glyph or label also carries the meaning |
| 2.4.7 Focus visible AA | partly | the theme picks the ring colour; the app decides whether a ring is drawn |
| 2.4.11 / 2.4.13 Focus appearance (2.2) | colour half only | ring size and shape are the app's; the 3:1 change-of-contrast test is the theme's |
| 1.4.8 Visual presentation AAA | one clause | the "user can select foreground and background" clause is met by the theme existing; nothing to audit |
| 1.4.12 Text spacing | no | spacing is markup |
| 1.3.x, 2.1.x, 2.4.3, 2.4.4, 4.1.x, 3.x | no | structure, keyboard order, labels, names. Do not spend time here |

## Read the build first

Do these three steps before measuring anything. They turn half the audit into a lookup.

1. Currency. `docs/CHECKS.md` is regenerated by `node build.mjs`. Trust it only when
   `node build.mjs --check` prints `0 errors` and `src/roles.json` and `src/palette.json`
   are not newer than `docs/CHECKS.md` (`ls -l --time-style=+%s`). If they are newer, ask the
   lead for a rebuilt CHECKS.md; do not run the full build yourself, it writes `ports/`.
2. Coverage. The build checks roles, not keys. Grep the port template for each key the table
   below names and confirm it resolves to the checked role (`{ui.focus}`, not `{ui.accent}`
   or a palette name). A key that bypasses the role is a finding even when the colour happens
   to pass.
3. Floors. `src/roles.json` sets `minContrast` (4.5 text, 3 structural), `minContrastWith`
   (on-colour pairs) and `carriesCode` (tinted backgrounds keep 65% or 85% of each syntax
   role's floor). A role with none of these is unchecked and is yours to measure.

What CHECKS.md proves per flavour, on `ui.background`, `ui.pane.secondary`, `ui.pane.tertiary`:
every `syntax.*` role, `ui.text`, `ui.text.muted`, `ui.link` at their floors; `ui.accent`,
`ui.focus`, `ui.border.*`, `ui.cursor` at 3:1 on `ui.background` only; every `on.*` pair at
4.5:1; syntax text over selection, current line, search and diff tints; syntax pair distance
at 5 OKLab x100.

What it does not check, measured on the palette of 2026-11-15 (worst flavour, on `ui.background`). These are a baseline, not a rule: if the palette has changed since, re-measure with `scripts/contrast.mjs` rather than filing a finding against the table:

| Unchecked role as text | Wisp | Fen | Mire | Blackwater | Verdict |
|---|---:|---:|---:|---:|---|
| `ui.success` `ui.warning` `ui.info` `ui.bell` | 5.6 | 7.8 | 9.4 | 10.6 | pass everywhere, also on both panes |
| `ui.error` | 5.67 | 4.99 | 5.32 | 6.05 | pass; Fen base is the tight one |
| `ui.text.subtle` | 3.46 | 3.33 | 4.40 | 4.38 | structural only; 2.80 on Wisp crust, so never text on `ui.pane.tertiary` |
| `ui.tab.indicator` (tint as text) | 4.75 | 5.55 | 6.56 | 7.46 | 4.26 on Wisp mantle, 3.84 on Wisp crust: tint is text on base only |
| `ui.mark1..3`, `terminal.color16/17` | 5.6 | 5.9 | 7.2 | 8.2 | pass |

## 1.4.3 contrast (minimum)

| Check | Where | Threshold | Finding when |
|---|---|---|---|
| Every text key resolves to a role with `minContrast` 4.5, or to a role in the table above that passes on the surface it sits on | template | 4.5:1 | a text key uses `ui.text.subtle`, a bright ANSI slot, `tint` off base, or a palette name |
| Text the app composes over a theme fill (host-owned pairings, STYLE_GUIDE step 5) | template header + frame | 4.5:1 per flavour | the header lists no measured ratio, or the frame shows `ui.text` on `ui.fill` (2.35 Wisp, 2.65 Fen) |
| Text on a tinted background the port uses that has no `carriesCode` | roles.json | 65% of floor | a new tint role was added without `carriesCode` |
| Large text (status line at 18pt+, overlay digits) | frame | 3:1 | under 3:1 only; 3 to 4.5 is a note |

Known exceptions, not findings: `ui.text.muted` on `ui.selection` is 4.34 on Fen (muted text is
not meant to be selected body text); `syntax.comment` on `ui.selection` is 3.33 on Fen, inside
the 65% `carriesCode` budget by design.

## 1.4.6 contrast (enhanced), AAA

Report, do not fail. `ui.text` reaches 7:1 on every surface in every flavour. No accent does
on Wisp (all sit at 5.6 to 6.5). Nothing a port can change.

## 1.4.11 non-text contrast

The ratio is against the colour the component sits on, not always `ui.background`. CHECKS.md
only tests `ui.background`. Measured against the panes here, so the auditor checks placement,
not maths.

| Component | Role | vs background | vs `pane.secondary` | vs `pane.tertiary` | What to check in the template |
|---|---|---|---|---|---|

| Input border, focused / active split | `ui.border.active` (= accent) | 4.5 / 3.5 / 3.5 / 3.8 | 4.0 / 4.1 / 3.8 / 4.0 | 3.6 / 4.6 / 4.0 / 4.1 | pass everywhere |

| Scrollbar thumb | `overlay0` (structural) | not checked | | | 1.4.11 exempts scrollbars drawn by the platform; a themed thumb under 3:1 is a note, not a finding |
| Text selection highlight | `ui.selection` vs `ui.background` | 1.37 / 1.42 / 1.38 / 1.36 | | | accepted exception, see below |
| Current line, search hits, diff lines, status surfaces | tints | 1.0 to 1.6 | | | accepted: these are `carriesCode` tints whose text keeps 4.5:1 |

Decision on the selection tint. A text selection at 1.4:1 is not a 1.4.11 failure here, for
three reasons. The selected text itself stays at 6.6:1 or better and keeps its syntax colour,
so the state is read from the text, not the tint. The caret marks the selection's edge. A
stronger tint would break the `carriesCode` budget and trade a 1.4.11 note for real 1.4.3
failures on every syntax role (a 35% tint left comments at 81% of floor). Row selection in
chrome has no text-keeps-colour argument, so it must be `ui.fill`, which passes.

Known exception: `ui.tab.inactive` on `ui.pane.tertiary` is 1.1:1 on Wisp and Fen. The text on
the tab is 6.1:1 and the active tab carries an indicator at 4.8:1 or better, so tab identity
is readable; the tab boundary is not. Record it, do not raise it against the port.

## 1.4.1 use of colour

Colour may not be the only cue. The theme cannot add a glyph, so the audit is: where does the
port make hue the only difference, and does that pair survive CVD (next section).

| Surface | Cue besides colour | Theme's duty |
|---|---|---|
| Diff added / removed text | `+` / `-` glyphs, line position | pair distance is secondary; the `ui.diff.*` backgrounds are 3 to 5 apart even for normal vision, by design (18% tints) |
| Diff gutter bar or dot with no glyph | none | pair must pass the CVD table or the finding goes to the template (add a shape) or the maintainer |
| Error vs warning diagnostics | icon, undercurl, severity text | Wisp warning/error under deuteranopia is 2.7; a port that colours only a gutter dot is a finding |
| Git status letters, listing colours (lsd, starship) | the letter itself | pass by the letter; colour is decoration |
| Red / green status with no text (a dot, a bar) | none | FAIL on Wisp under deuteranopia (5.6 is under the 10 warn line); ask the port for a shape or text |
| Search hit vs replace preview (`mark1` / `mark2`) | position, the replace panel | marks are 1.5 to 5.1 apart under prot/deut in every flavour; never rely on mark hue alone |

## 2.4.7, 2.4.11, 2.4.13 focus

| Check | Threshold | Status |
|---|---|---|
| Focus ring colour against the surface it sits on (2.4.11 minimum) | 3:1 | passes on all three panes in every flavour (table above) |
| Change of contrast between focused and unfocused state (2.4.13) | 3:1 between `ui.focus` and `ui.border.inactive` | 1.20 to 1.34:1. Focus is a hue change, not a luminance change. Passes 2.4.11 (ring vs surface) but not 2.4.13's enhanced test. Palette-wide, informational |
| Ring on a filled button | 3:1 vs the fill | fails (1.0 to 1.5). Port must draw the ring outside the button or use `ui.on.fill` inside |
| Ring drawn at all | n/a | app's duty; note if the frame shows a focused field with no ring, so the port can set the key |
| Focus not conveyed by `ui.accent` alone | n/a | accent is also hover and active border; a port that uses it for focus loses the distinction. Finding, template layer |

## Colour-vision deficiency

Thresholds: a meaning pair under 5 OKLab x100 in any simulated condition fails; under 10
warns. 5 is the build's own floor for syntax pairs, calibrated on Catppuccin's closest pair
(5.7). Status colours are compared from memory, not side by side like syntax tokens, so they
get twice the room. Simulation is Machado et al. 2009 at severity 1.0 (dichromacy, the worst
case) in linear RGB; `scripts/cvd.mjs` prints the four conditions and the contrast ratio.

Baseline for the current palette (norm, then worst condition). Mire and Blackwater share
accents, so their rows are identical. These are palette facts; a port inherits them and is
only at fault where it makes hue the sole cue.

| Pair | Wisp | Fen | Mire / Blackwater |
|---|---|---|---|
| `ui.success` / `ui.error` (= `ansi.1`/`2`) | 26.6, deut 5.6 warn | 23.1, deut 11.1 ok | 27.4, deut 13.9 ok |
| `ui.warning` / `ui.error` | 15.2, deut 2.7 FAIL | 17.8, deut 12.1 ok | 21.7, deut 15.4 ok |
| `ui.diff.added` / `ui.diff.removed` | 3.1, deut 0.5 FAIL | 3.7, deut 1.3 FAIL | 4.7, deut 1.9 FAIL |
| `syntax.diff.removed` / `ui.success` | 19.8, deut 4.1 FAIL | 17.6, deut 7.5 warn | 20.8, deut 8.7 warn |
| `ui.info` / `ui.success` | 6.9, trit 1.9 FAIL | 5.6, trit 2.0 FAIL | 6.0, trit 2.1 FAIL |
| `ansi.9` / `ansi.10` | 26.4, deut 5.9 warn | 26.1, deut 10.0 warn | 29.8, deut 12.4 ok |
| `ui.mark1` / `ui.mark2` | 5.9, deut 1.5 FAIL | 6.7, prot 5.1 warn | 6.1, prot 4.1 FAIL |
| `ui.mark2` / `ui.mark3` | 16.9, deut 2.9 FAIL | 11.5, prot 2.6 FAIL | 12.7, prot 2.8 FAIL |
| `ui.mark1` / `ui.mark3` | 11.1, deut 1.9 FAIL | 7.7, deut 1.2 FAIL | 7.7, prot 1.3 FAIL |

How to read it. Dark flavours keep success / warning / error apart for every CVD type. Wisp
does not: its warning and error merge under deuteranopia, and success and error come close.
Info versus success is a teal versus green pair and merges under tritanopia everywhere. The
three marks and the two diff tints are not CVD-safe in any flavour. A port finding cites this
table and says which surface relies on the failing pair with no second cue.

## Sampling colours off a frame

The frames are 1200x750 VP8 WebP with 4:2:0 chroma subsampling. Chroma is stored at half
resolution, so a one-pixel glyph stem has its hue averaged with the background. Rules:

- Prefer the role hex from `docs/ROLES.md` and measure with `scripts/contrast.mjs`. Sample the
  frame only to confirm which role a surface is, not to get the number.
- When you must sample text, take the mode of the darkest (dark text) or lightest (light text)
  pixels inside a bold or wide glyph, never an edge, a serif or a thin stroke. Antialiasing
  blends toward the background and inflates the apparent contrast of a failing pair.
- Sample backgrounds at least 4 px from any edge or text, in a flat 8x8 patch.
- A sampled value within 3 units (0 to 255) of a role hex is that role. Further off means the
  app composed it (alpha, hover, a gradient): that is the pairing the build cannot see, so
  measure it and name the host colour.
- Do not sample from a PNG that has been through WebP and back; use the capture PNG when it
  exists in the review folder.

## Reporting a finding

Use the panel's finding format in `review.md`; put these fields in it. Worst first. Separate port findings from palette facts (anything in
the baseline tables above goes under a "known, palette-wide" heading, not against the port).

```
SC 1.4.11 | Fen | settings dialog, focused toggle | ui.focus on ui.fill | 1.26:1 | 3:1 | template: draw ring on the dialog surface
SC 1.4.3  | Wisp | sidebar footer | ui.text.subtle on ui.pane.tertiary | 2.80:1 | 4.5:1 | template: use ui.text.muted
SC 1.4.1  | all  | git gutter dot | ui.warning vs ui.error, deut 2.7 | 5 | template: add shape, or override with a glyph
```

Fields: SC, flavour, surface, pair (roles, not hexes, when the template names roles),
measured, threshold, layer of fix (palette, role, template, override, app). A measured value
that comes from a frame sample says so. A pass needs no line.
